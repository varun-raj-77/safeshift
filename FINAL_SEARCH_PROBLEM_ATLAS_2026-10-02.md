**Final problem search: atlas of 50 problem areas — 2 October 2026**

This is the breadth and elimination record for the [final decision](<C:/Users/rekha/OneDrive/Desktop/PROJECT AVEN/FINAL_PROJECT_SEARCH_2026-10-02.md>). The [scorecards](<C:/Users/rekha/OneDrive/Desktop/PROJECT AVEN/FINAL_SEARCH_SCORECARDS_2026-10-02.md>) deepen the 15 survivors. The search ignores the owner's career, skills, available hours, and desired portfolio timeline.

Each entry identifies a broken outcome, affected users, existing approaches and their limits, the technical barrier, current relevance, a possible engineering response, and the unresolved contribution. “Advance” means investigate further, not recommend building. “Eliminate” means the present proposal did not beat the shortlist; it does not mean the underlying problem is unimportant. Exactly 15 advance and 35 are eliminated here.

Frequency is not inferred from isolated incidents. The later scorecards distinguish routine exposure from observed failures and state where prevalence is unknown. Sources establish problems and prior art; proposed gaps are hypotheses unless explicitly documented. Mature tools can be strong and still leave worthwhile work.

**Infrastructure continuity and reliability**

**P01. Recovering an internally consistent application after disaster — ADVANCE.** Operators can restore individual resources yet recover incompatible business state across databases, queues, objects, and external services. Veeam, Rubrik, Commvault, and AWS already test recovery; another restore scheduler is unnecessary. The technical barrier is establishing which states can coexist and which transactions must be reconciled. More heterogeneous services increase the number of boundaries. A project could validate recovery against cross-service invariants and dependency-loss scenarios. The unresolved opportunity is repeatable, economical application-level evidence rather than a new claim to have invented recovery testing. [AWS](https://docs.aws.amazon.com/aws-backup/latest/devguide/restore-testing.html), [consistent recovery research](https://design.inf.usi.ch/bac).

**P02. Services silently violating their own semantics — ADVANCE.** Operators see healthy processes while application behavior is wrong. Monitoring, Jepsen, formal specifications, and deterministic testing help; translating intended behavior into cheap executable checks remains difficult. T2C already derives runtime semantic checkers from tests, so that mechanism is prior art. The technical interest is sound generalization, distributed observations, and overhead. Automated development makes stronger checks more valuable but did not create the problem. A project could extend checker coverage to useful unsupported stateful contracts and measure detection against known failures. [T2C](https://www.usenix.org/conference/osdi25/presentation/lou), [Antithesis assertions](https://antithesis.com/docs/product/writing_tests/assertions/).

**P03. Hardware silently corrupting computations — ADVANCE.** Datacenter operators and scientific users can receive incorrect values without a crash. ECC, diagnostics, and redundancy are substantial defenses; they do not observe every compute path. A 2026 GPU fault study illustrates the complexity of realistic error models. The barrier is affordable detection with credible coverage and attribution, not merely injecting random bit flips. Larger accelerator deployments increase exposure. A project could combine workload-aware checks with fault localization and a reproducible fault corpus. Unresolved: how well simulated faults predict actual defects. [GPU error study](https://arxiv.org/abs/2605.04213), [NVIDIA diagnostics](https://docs.nvidia.com/datacenter/dcgm/latest/learn/modules/dcgm-diagnostics.html).

**P04. Stateful upgrades that cannot safely roll back — ELIMINATE.** Service teams can revert binaries after a bad release but not necessarily reverse schema changes or external effects. Atlas and pgroll already address important migration risks. The difficult part is compatibility across old/new application versions and irreversible effects. Continuous deployment keeps the problem relevant. A proposed project would rehearse version transitions and check business invariants. Residual opportunity exists, but a generic migration platform duplicates established tooling; no stronger new mechanism emerged in this search. [Atlas migration testing](https://www.atlasgo.io/testing/migrate), [pgroll](https://xata.io/blog/multi-version-schema-migrations).

**P05. A successful write not surviving a crash — ELIMINATE.** Storage users rely on durability contracts whose implementation spans filesystems, caches, and devices. CrashMonkey-style testing and newer research such as Silhouette attack these failures. The challenge is exploring persistence reorderings with a faithful oracle. New storage architectures keep old assumptions unstable. A focused project could verify one storage stack's promised durability. The problem deserves continued work, but a new general checker needs a specific supported-stack or coverage advance; “crash it and inspect files” is not that advance. [Silhouette](https://www.usenix.org/conference/fast25/presentation/jiao), [Open CAS case study](https://www.usenix.org/conference/atc25/presentation/duan-shaohua).

**Compilers, languages, and computation**

**P06. Fast numerical code producing unacceptable answers — ADVANCE.** Scientists and kernel developers need acceptable numerical behavior across inputs, precisions, compiler versions, and hardware. A close match on sampled inputs is insufficient; exact bit equality is often the wrong requirement. Herbie, FLiT, GPU tools, and recent contract-oriented verifiers already contribute. The barrier is a useful accuracy contract and an independent oracle at reasonable cost. Mixed precision and generated kernels increase relevance. A project could connect explicit numerical contracts to counterexamples and honest verification coverage. [Herbie's error model](https://herbie.uwplse.org/doc/latest/error.html), [GPU contract verifier](https://arxiv.org/abs/2608.12700).

**P07. Compiler optimizations changing program meaning — ADVANCE.** Compiler users can get wrong executable behavior from apparently valid source. Alive2 and CompCert show that checking or proving transformations is possible within defined semantics. The remaining barriers include language coverage, undefined behavior, target-specific lowering, and scalability. More optimization pipelines and accelerators enlarge the surface. A project could validate an important unsupported transformation family and produce independently checkable counterexamples. The contribution must improve coverage or guarantees rather than wrap a compiler in random tests. [Alive2](https://github.com/AliveToolkit/alive2/blob/master/README.md), [Triton miscompilation report](https://github.com/triton-lang/triton/issues/10821).

**P08. Removing memory-unsafe legacy code without introducing behavioral regressions — ADVANCE.** Maintainers need safer implementations while preserving compatibility, performance, and decades of behavior. C2Rust assists translation, while manual ports demonstrate viable replacements. VERT, &inator, and funded programs already tackle stronger guarantees. Ownership, aliasing, callbacks, observable effects, and the validity of proof assumptions remain difficult. Improved Rust verification tools make progress timely. A project could make module-by-module migrations and their subsequent maintenance verifiable and economical. A generic “AI translates C to Rust” product contributes too little. [C2Rust](https://github.com/immunant/c2rust), [&inator](https://arxiv.org/abs/2604.17261).

**P09. Concurrency bugs hidden by ordinary execution — ELIMINATE.** Library developers cannot infer correctness from many successful runs. Loom and Shuttle already explore schedules; model fidelity and state-space explosion limit coverage. The technical barrier is preserving relevant memory-order semantics while bounding exploration. More concurrent runtimes keep this useful. A project could add a missing memory-model or runtime integration with measured bug yield. The broad proposal lacks a differentiating mechanism and is better framed as an upstream research contribution. [Shuttle](https://github.com/awslabs/shuttle), [Loom issue tracker](https://github.com/tokio-rs/loom/issues).

**P10. Trusting a binary's relationship to its claimed source — ELIMINATE.** Software consumers face tampered builds and unverifiable release processes. Reproducible builds and Sigstore address complementary parts; a signature proves a claim's origin, not its truth or program safety. Bootstrapping and nondeterministic toolchains are hard. Supply-chain automation increases the stakes. A project could close a concrete reproducibility gap or reduce trusted build inputs. The generic provenance platform is well occupied, and a stronger unsolved subset was not established. [Sigstore](https://docs.sigstore.dev/quickstart/quickstart-cosign/), [Reproducible Builds](https://reproducible-builds.org/).

**Data systems and financial infrastructure**

**P11. Internal records disagreeing with external money movements — ADVANCE.** Finance operators must reconcile bank statements, processors, internal ledgers, fees, and reversals. Modern Treasury, Formance, and specialist teams already automate substantial work. The hard residue is ambiguous identifiers, timing, missing evidence, and exceptions; balanced totals can conceal transaction-level errors. More providers multiply reconciliation boundaries. A proposed system would verify causal links and make unresolved discrepancies explicit. The research question is whether a reusable formal model beats provider-specific rules, not whether reconciliation exists. [Formance](https://www.formance.com/platform/reconciliation), [Modern Treasury](https://docs.moderntreasury.com/ledgers/docs/account-reconciliation).

**P12. Databases returning logically incorrect query results — ADVANCE.** Application and analytics users depend on database semantics that may fail without crashing. SQLancer already has substantial documented impact, and Jepsen investigates consistency. The difficult gap is oracles for increasingly complex operators, types, transactions, and optimizer interactions. New engines and features keep this relevant. A project could introduce an oracle for a neglected semantic family and integrate it upstream. Another undifferentiated SQL fuzzer would be weak; accepted real bug reports and a validated oracle would be strong. [SQLancer](https://sqlancer.github.io/), [Jepsen analyses](https://jepsen.io/analyses).

**P13. Data schemas changing while their meaning silently changes too — ELIMINATE.** Data consumers can accept structurally valid records with altered definitions, units, or aggregation rules. Schema registries, SQLMesh tests, and data contracts help but require explicit business semantics. The hard problem is deciding which changes are intended. Rapid pipeline evolution increases exposure. A project could enforce domain-specific semantic contracts and compare before/after outputs. Without domain owners and a clear oracle, the general solution becomes a dashboard plus guesses; specialized clinical semantics proceeds separately. [SQLMesh tests](https://sqlmesh.readthedocs.io/en/latest/concepts/tests/).

**P14. Duplicate, late, or reordered events corrupting derived state — ELIMINATE.** Streaming applications can diverge under retries and backfills. Flink, Debezium, and Materialize already offer mature mechanisms with explicit boundaries. The barrier is end-to-end correctness across sinks that cannot share transactions, plus application meaning of late data. More event-driven services increase relevance. A project could verify a bounded source/sink combination under failures. A new generic exactly-once layer would conceal assumptions and duplicate infrastructure. [Flink](https://flink.apache.org/2018/02/28/an-overview-of-end-to-end-exactly-once-processing-in-apache-flink-with-apache-kafka-too/), [Materialize self-correction](https://materialize.com/blog/self-correcting-materialized-views/).

**P15. Being unable to explain which inputs produced an output — ELIMINATE.** Researchers and data teams struggle with missing lineage across transformations. OpenLineage and reproducible workflow tools provide substantial infrastructure. Dynamic dependencies and external state remain difficult. More derived and AI-produced data increase the need. A project could verify rebuild dependency completeness in one stack. The unresolved abstraction is not simply a graph; it is trustworthy, operational lineage. No clear independent advantage justified a new general platform. [OpenLineage](https://openlineage.io/), [Software Heritage](https://www.softwareheritage.org/software-heritage-faq/).

**Privacy, authority, and identity**

**P16. Deleted personal information reappearing in copies or derived data — ADVANCE.** People and data operators need deletion to survive rebuilds, caches, and restores. Fides/Lethe and data catalogs already execute deletion workflows. The hard boundary is unknown or irreversible derivations and replicas outside control. New embedding, summary, and training pipelines expand the surface. A project could track declared derivations, test resurrection, and issue scoped deletion evidence. Universal deletion cannot be inferred from an API success response. Exact machine unlearning is a distinct problem considered in P50. [Lethe](https://www.ethyca.com/lethe), [OpenLineage](https://openlineage.io/).

**P17. Combining organizations' records without exposing their raw data — ELIMINATE.** Health and financial analysts need linkage while minimizing disclosure. Private set intersection, secure computation, differential privacy, and specialist services exist. Identity errors, threat models, utility loss, and side information remain hard. Cross-institution analytics makes the need durable. A project could benchmark privacy-preserving linkage for a defined data regime. The search did not establish an important new mechanism or accessible ground truth; this is a serious research field, not an automatic product gap. [NIST entity alignment discussion](https://www.nist.gov/blogs/cybersecurity-insights/protecting-model-updates-privacy-preserving-federated-learning-part-two).

**P18. Delegated software acting after authority changes — ADVANCE.** Agent adopters need permissions to remain correct across delegation, retries, revocation, and external effects. Gateways, identity products, and major-lab sandboxes already enforce meaningful controls. The hard problem is complete mediation and precise authority/effect semantics across systems. Autonomous agents amplify an established security problem. A model-independent trust runtime could supply a common enforceable contract and conformance suite. It must not confuse authenticating a tool call with authorizing everything the tool can do. [NIST initiative](https://www.nccoe.nist.gov/projects/software-and-ai-agent-identity-and-authorization), [Agentgateway](https://agentgateway.dev/docs/kubernetes/latest/documentation/security/authorization/).

**P19. Changing access rights during offline encrypted collaboration — ADVANCE.** Collaborators need availability while devices disagree about membership. Keyhive and related capability systems address this directly. Revocation cannot retract plaintext already disclosed, and partitions constrain the speed of new authorization decisions. The technical issue is explicit semantics for future access, concurrent histories, and key changes. Growing local-first software makes the boundary important. A project could prove and test a protocol against declared partition and compromise models. The contribution must improve guarantees or usability beyond ongoing work. [Keyhive API](https://automerge.org/docs/keyhive/ark-api-guide/).

**P20. Recovering digital identity without enabling takeover or surveillance — ELIMINATE.** Users lose authenticators; service operators balance recovery, fraud resistance, privacy, and support burden. Passkeys, recovery codes, identity providers, and credential standards cover much of the landscape. Human identity proof and abuse economics are harder than cryptographic key rotation. More digital services make the need durable. A project could evaluate one recovery protocol with explicit threats. No universal technical solution can infer rightful ownership from insufficient evidence; adoption and human procedures dominate this broad proposal. [W3C credential status mechanisms](https://www.w3.org/community/reports/credentials/CG-FINAL-vc-status-list-2021-20230102/).

**Networks, infrastructure control, and operating boundaries**

**P21. A safe network configuration producing an unsafe transition — ADVANCE.** Network operators can validate a final policy yet encounter failures during deployment or convergence. Batfish and research verifiers already cover substantial configuration semantics. The residual challenge combines transient states, devices' actual behavior, and observations under change. Frequent automated configuration increases relevance. A project could verify or test transition plans for a declared protocol/device set. It must distinguish model guarantees from real firmware behavior. A generic static reachability checker would duplicate mature prior art. [Batfish](https://github.com/batfish/batfish), [network test pyramid](https://batfish.org/2021/06/16/the-networking-test-pyramid.html).

**P22. Internet routing security depending on inconsistent deployment — ELIMINATE.** Network users can lose reachability after route leaks, hijacks, or misconfiguration. RPKI and routing policies reduce risk, but implementation and deployment errors remain. The technical interest is distributed trust, stale validation state, and safe update behavior. The problem is persistent rather than new. A project could test RPKI implementation conformance and operational transitions. Existing standards identify concrete issues; the strongest path is targeted implementation improvement, not a replacement global routing-security platform. [RFC 8481](https://www.rfc-editor.org/info/rfc8481/), [RFC 9324](https://www.rfc-editor.org/info/rfc9324/).

**P23. Misunderstanding effective access across cloud services — ELIMINATE.** Security teams cannot safely reason from one policy file when permissions interact across identities, resources, and networks. AWS Access Analyzer and Zelkova demonstrate substantial automated reasoning. Cross-cloud semantic differences remain hard. More identities and automation increase exposure. A project could verify a specific unsupported combination and explain counterexamples. The broad permission-graph product is crowded, and integration breadth alone is not an unusually strong contribution. [AWS Security Reference Architecture](https://docs.aws.amazon.com/pdfs/prescriptive-guidance/latest/security-reference-architecture/security-reference-architecture.pdf).

**P24. Extending applications with untrusted code safely — ELIMINATE.** Hosts need plugins without handing them every privilege. OS isolation and WebAssembly components already provide useful boundaries. Host imports, shared resources, and capability design remain the difficult part. Agent-created tools increase urgency but do not invalidate existing sandbox research. A project could supply a verified host-interface subset with resource guarantees. “Run plugins in Wasm” is not enough; the broad runtime proposal overlaps established work and P18's more specific authority question. [WebAssembly component model](https://component-model.bytecodealliance.org/design/components.html).

**P25. Validly signed changes causing fleet-wide failure — ELIMINATE.** Operators can authenticate a configuration that is still operationally disastrous. Rollout systems, canaries, and staged deployment are mature; predicting blast radius and catching correlated failures remain hard. Cloudflare's recent resilience work illustrates continuing need. A project could test configuration semantics before broad propagation. The barrier is system-specific outcome modeling, not a missing signature layer. A general platform lacked a stronger justified mechanism than existing staged rollout plus explicit invariants. [Cloudflare resilience plan](https://blog.cloudflare.com/fail-small-resilience-plan/).

**Healthcare infrastructure**

**P26. Linking medical records to the correct person — ELIMINATE.** Patients and clinicians suffer from fragmented or incorrectly merged records. Enterprise master-patient indexes and matching standards are established; ambiguous demographics and incomplete identifiers prevent perfect resolution. Interoperability expands the number of matches. A project could produce privacy-aware uncertainty estimates and adjudication tooling. The technical problem is important, but the broad project depends on ground truth, institutional participation, and workflow design more than a newly identified algorithmic gap. Do not turn uncertain matches into automatic clinical facts. [ONC patient matching](https://healthit.gov/standards-and-technology/patient-identity-and-patient-record-matching/).

**P27. Clinical data exchanging successfully but changing meaning — ADVANCE.** Clinicians and researchers can receive valid messages with mismatched codes, units, temporal meaning, or context. FHIR validators, terminology services, Rhapsody, and OHDSI tooling already help. The barrier is validating meaning against contextual clinical intent; format conformance cannot supply that oracle. Interoperability and downstream automation increase the stakes. A project could make expert-reviewed semantic mappings executable, versioned, and testable against adjudicated examples. The unresolved value is dependable change validation, not automatic universal medical understanding. [FHIR validation](https://hl7.org/fhir/R4/validation.html), [OHDSI data quality](https://ohdsi.github.io/TheBookOfOhdsi/DataQuality.html).

**P28. Important test results failing to reach responsible follow-up — ELIMINATE.** Patients can receive delayed care when results are delivered but not acted on. Portals, alerts, and clinical workflow systems exist; responsibility across care settings can remain unclear. The hard part is closed-loop accountability without alert fatigue. Electronic result access alone does not settle the workflow. A project could track acknowledgements, handoffs, and exceptions. The need is serious, but organizational authority and clinical integration dominate; the search did not justify an independent general software winner. [AHRQ test-result communication](https://www.ahrq.gov/diagnostic-safety/resources/issue-briefs/dxsafety-test-result-communication2.html).

**P29. Inconsistent medication lists across care transitions — ELIMINATE.** Patients, pharmacists, and clinicians must reconcile intended, prescribed, dispensed, and actually taken medicines. EHR reconciliation workflows help, but conflicting sources and patient behavior require judgment. The technical interest is temporal provenance and uncertainty, not merely matching names. Cross-provider care sustains the need. A proposed system could present evidence and unresolved conflicts. Without expert workflow validation, automation risks producing confidently wrong lists; P27 offers a more clearly bounded infrastructure contribution. [AHRQ medication reconciliation](https://digital.ahrq.gov/medication-reconciliation).

**P30. Medical devices interpreting exchanged data incorrectly — ELIMINATE.** Device makers and hospitals need safe interoperability across interfaces and timing assumptions. FDA guidance and standards already articulate the shared problem. Device-specific semantics, timing, failures, and hardware behavior make verification difficult. Connected devices increase exposure. A project could build conformance and fault-injection tests for one device protocol. This is worthwhile engineering, but a general project would require a tightly selected protocol and clinical/device partners before its distinctive contribution could be established. [FDA interoperability](https://www.fda.gov/medical-devices/digital-health-center-excellence/medical-device-interoperability).

**Accessibility and education**

**P31. An interface passes automated checks but remains unusable with assistive technology — ADVANCE.** Disabled users face failures in focus, announcements, navigation, and complete workflows. Deque and ARIA-AT already cover meaningful guided testing and interoperability. The barrier is task semantics across browser/assistive-technology combinations, plus human judgments that resist universal automation. Dynamic interfaces and frequent updates enlarge the test surface. A project could turn user-validated task expectations into reproducible cross-platform regressions. It must extend standards work, not promise that a scan certifies accessibility. [ARIA-AT](https://w3c.github.io/aria-at/), [Deque guided testing](https://www.deque.com/blog/intelligent-automation-and-the-new-era-of-guided-testing/).

**P32. Documents losing usable structure for assistive technology — ELIMINATE.** Readers encounter inaccessible reading order, tables, mathematics, and navigation in PDFs. PDF/UA tooling, remediation products, and authoring standards exist. Recovering intended structure and meaningful descriptions requires semantic judgment. Large document backlogs sustain the need. A project could validate one difficult class such as technical tables through human-reviewed structure. A broad automatic remediator would overclaim, and its contribution is weaker without a specific corpus and measurable advantage. [PDF Association techniques](https://pdfa.org/techniques-for-accessible-pdf/).

**P33. Learning systems depending on reliable internet — ELIMINATE.** Learners and teachers in low-connectivity settings need content, progress tracking, and synchronization. Kolibri already provides a substantial offline-first ecosystem. Device constraints, content distribution, and intermittent identity synchronization remain difficult. The need persists independently of AI. A project could improve a specific deployment failure, but another general offline school platform would duplicate existing work. KA Lite's replacement by Kolibri also illustrates why maintenance and deployment matter as much as novelty. [Kolibri](https://learningequality.org/kolibri/about-kolibri/), [KA Lite transition](https://kalite.learningequality.org/).

**P34. Educational software measuring activity rather than learning — ELIMINATE.** Learners and educators need evidence that an intervention improves understanding and transfer. Assessments, educational studies, and existing learning platforms provide partial answers; completion metrics do not prove learning. The barrier is causal evaluation across different contexts and students. Growing digital provision makes measurement important. A project could support controlled evaluation with transparent assessment design. This is an important empirical problem, but a general engineering system cannot substitute for educational science or good experimental design. [Learning Equality impact work](https://learningequality.org/impact/our-impact/).

**P35. Real-time speech access failing on important words and contexts — ELIMINATE.** Deaf and hard-of-hearing users need useful captions, not merely low average word error. Speech-recognition systems and human captioning services already help. A single incorrect word can change meaning, and live delivery constrains correction time. Remote and hybrid interaction keeps demand durable. A project could provide domain-specific confidence and human correction workflows. The unresolved contribution requires task-level user evaluation; generic transcription plus a language model is too weak. [W3C on caption accuracy](https://w3c.github.io/wai-website/media/av/captions/), [live-caption guidance](https://www.w3.org/WAI/WCAG21/Understanding/captions-live).

**Science, robotics, and physical infrastructure**

**P36. Published computational results not being reproducible later — ELIMINATE.** Researchers lose dependencies, data versions, environments, and manual steps. Software Heritage, workflow systems, containers, and archival practices address different layers. Re-execution does not establish scientific validity. The hard part is preserving complete, lawful, usable execution context over time. Software rot keeps the need active. A project could produce reproducible artifacts for one scientific workflow class. The generic “reproduce any paper” system remains too underspecified; P06 supplies a sharper correctness problem. [Software Heritage](https://www.softwareheritage.org/software-heritage-faq/), [SciRep research](https://doi.org/10.1016/j.future.2025.107924).

**P37. Robot behavior validated in simulation failing in reality — ELIMINATE.** Robot operators cannot assume simulated success transfers to physical conditions. NIST test methods and extensive sim-to-real research already address this. Model discrepancy, sensing, contact dynamics, and distribution shift remain barriers. Wider embodied automation increases relevance. A project could quantify simulator validity for one operational envelope and reject unsupported claims. This is deeply worthwhile, but a general verification product cannot create missing physical ground truth; the search did not identify a superior specific intervention. [NIST robotics measurement](https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=958147), [reality-gap review](https://doi.org/10.1146/annurev-control-031924-100130).

**P38. Manufacturing design intent being lost across engineering tools — ELIMINATE.** Manufacturers need geometry, tolerances, inspection, and production data to stay consistent. STEP/QIF and industrial platforms exist. Semantic conformance testing still includes substantial manual work. More distributed manufacturing increases exchange boundaries. A project could validate a narrow design-to-inspection transformation with traceable counterexamples. The technical barrier is preserving meaning across models, but industrial data access and a chosen standard are essential; no sufficiently evidenced general product gap emerged. [NIST digital thread](https://www.nist.gov/programs-projects/digital-thread-manufacturing).

**P39. Grid studies and control integration lagging infrastructure change — ELIMINATE.** Utilities and energy developers face complex integration studies, model exchange, and control coordination. NREL tools and DOE initiatives address substantial parts. Data quality, physical uncertainty, study dependencies, and institutional processes limit progress. Distributed resources and new connections increase pressure. A project could make one simulation exchange reproducible and verifiable. The broad problem is not reducible to missing software, and this search does not establish that another simulation platform is the right intervention. [NREL tools](https://www.nrel.gov/grid/modeling-tools), [DOE interconnection roadmap](https://www.energy.gov/cmei/i2x/doe-distributed-energy-resource-interconnection-roadmap).

**P40. Scientific data carrying values without trustworthy units and uncertainty — ELIMINATE.** Scientists and engineers can combine incompatible measurements and silently overstate precision. Standards, calibration practices, and quantity libraries help; BIPM released a stable machine-readable SI Reference Point in June 2026. The difficult residue includes instrument history, uncertainty propagation, and context that was never recorded. Cross-domain data reuse increases relevance. A project could enforce measurement contracts for a specific pipeline. This deserves domain-specific work, but a general metadata platform would duplicate standards efforts and cannot reconstruct absent evidence. [BIPM digital-measurement resolution](https://www.bipm.org/en/-/resolution-cgpm-27-2), [SI Reference Point release](https://www.bipm.org/en/-/2026-06-18-the-first-stable-version-of-the-si-reference-point).

**Human continuity and collaboration**

**P41. Repeatedly teaching software who its owner is and how their needs change — ADVANCE: FULL AVEN.** Owners need continuity, correct contextual learning, and bounded action. Letta, Hermes, and personal-agent products already supply substantial state and skill functionality. The unresolved endpoint is reliable long-term adaptation, including non-application, changing preferences, procedures, and model swaps, without authority drift. Long-running agents increase relevance. Full AVEN could integrate those outcomes, controlled improvement, and justified later self-model/affect research. Difficulty is not a penalty to its successful endpoint; architecture alone is not evidence of contribution. [Letta](https://docs.letta.com/concepts/stateful-agents), [memory evaluation](https://www.letta.com/blog/evaluating-memory-in-production-agents/).

**P42. Account transitions exposing or using the wrong user's state — ELIMINATE: TENANTSCOPE.** SaaS users and operators suffer when delayed requests or retained state cross account boundaries. Escape, custom Playwright tests, and scheduling tools already address adjacent and overlapping checks. The difficult residue is a useful transition oracle and economical integration. Richer client state sustains the need. TenantScope could package reproducible temporal isolation checks well. Without its former career-fit advantage, the contribution is narrower and more easily absorbed than the strongest infrastructure problems; this is not a finding that the bugs are harmless. [Escape](https://escape.tech/blog/escape-dast-multi-user-testing-tenant-isolation/), [TanStack discussion](https://github.com/TanStack/query/discussions/7728).

**P43. Concurrent edits merging correctly as data but incorrectly as human intent — ELIMINATE.** Collaborators can receive structurally converged documents that combine incompatible intentions. CRDTs and collaboration products solve convergence, not universal intent. The hard part is determining which conflicts require human choice. More offline and concurrent work sustains relevance. A project could expose meaningful conflicts for one document type and evaluate resolution quality. A general intent-preserving merge engine lacks an objective oracle; domain-specific UX research is the more honest route. [Ink & Switch local-first work](https://www.inkandswitch.com/essay/local-first/).

**P44. Crisis-response records being hard to combine or reconcile — ELIMINATE.** Responders need coherent information despite disconnected teams, changing schemas, and uncertain provenance. Humanitarian data platforms and HXL attempted standardization. The Centre for Humanitarian Data retired HXL support in January 2026, a concrete warning that useful standards need sustained adoption. A project could support one recurring field workflow with explicit conflict handling. The barriers include operational ownership and incomplete ground truth. No generic new standard should be proposed without understanding those deployment lessons. [HXL retirement](https://centre.humdata.org/retiring-hxl-services/).

**P45. Leaving a software provider without losing usable personal state — ELIMINATE.** Individuals can export files yet lose relationships, permissions, history, and application meaning. Solid provides interoperability protocols; provider exports vary. The technical interest lies in shared semantics and safe authority transfer. More accumulated digital state makes exit costly. A project could demonstrate faithful migration between two real applications. A universal personal data layer depends on adoption and incentives that software alone cannot force. AVEN's owner-state portability remains one bounded instance, not a solution to the entire problem. [Solid interoperability](https://solidproject.org/TR/sai).

**AI, evidence, and delegated computation**

**P46. An agent repeating an action after an ambiguous outcome — ELIMINATE.** Users can be charged twice or receive duplicate actions when a response disappears after commitment. Idempotency, durable execution, reconciliation, and tools such as Chaosline already address the problem. The barrier is external commitment that cannot be inferred from transport success. More tool-using agents increase exposure. A project could test unsupported effect classes against an external ledger. The broad proposed tester has close prior art; execution honesty is not a substitute for effect correctness. [Chaosline](https://github.com/navyabijoy/chaosline), [Temporal](https://learn.temporal.io/tutorials/python/standalone-activities/).

**P47. Evaluation scores overstating real AI capability — ELIMINATE.** Researchers and buyers face contamination, grader gaming, and mismatched tasks. NIST, benchmark maintainers, and evaluation platforms already investigate these failures. The difficult part is a valid, independent task oracle and representative sampling. Agent internet access and automated optimization worsen contamination risk. A project could build a sequestered domain benchmark with explicit validity checks. A generic evaluator cannot supply universal ground truth; the contribution must be domain-specific and experimentally demonstrated. [NIST evaluation failures](https://www.nist.gov/caissi/cheating-ai-agent-evaluations).

**P48. Remote computation being difficult to audit — ELIMINATE.** Customers may need evidence that a provider ran the claimed computation. Cryptographic proofs, TEEs, and systems such as AFTUNE tackle different trust/cost tradeoffs. Scaling proofs and defining the claimed computation remain difficult. Outsourced accelerator work increases relevance. A project could improve one verification cost/coverage frontier. This is substantial research, but a general “prove every remote AI action” product hides assumptions about inputs, semantics, and trusted hardware. [AFTUNE](https://www.usenix.org/conference/usenixsecurity26/presentation/jin).

**P49. Authentic media provenance being confused with factual truth — ELIMINATE.** Audiences and publishers need evidence about content origin and edits. C2PA already standardizes signed provenance. Missing metadata, untrusted signers, and truthful-but-misleading context remain hard. Synthetic media increases demand. A project could improve provenance preservation or explain evidence gaps. It cannot infer truth from a signature, and a universal authenticity detector is an unsupported promise. Existing standards provide a stronger contribution path than another proprietary authenticity badge. [C2PA explainer](https://spec.c2pa.org/specifications/specifications/2.2/explainer/Explainer.html).

**P50. Verifying that a trained model has forgotten selected information — ELIMINATE.** Data owners and model operators need meaningful removal claims. Retraining and unlearning techniques exist, but behavioral probes do not necessarily establish removal of influence. Formal definitions, adaptive training, and indistinguishability make the problem deep. Model deployment expands demand. A project could test a precisely defined unlearning guarantee and identify impossibility boundaries. The universal promise is underspecified and can be impossible under particular definitions; useful negative results are more credible than a generic erasure API. [Verification research](https://arxiv.org/abs/2408.00929), [retrain-equivalence limits](https://arxiv.org/abs/2510.16629).
